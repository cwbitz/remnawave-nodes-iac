# AGENTS.md

Ansible control node that manages the **Remnawave proxy Nodes** — the
`remnawave/node` containers a Remnawave Panel pushes Xray-core proxy
configuration to — on Debian-family VPSes, from a blank first boot: host
bootstrap, NetBird overlay join, host monitoring/security, then the Remnawave
Node. Idempotent and version-controlled.

## Project boundaries

This project owns **only the nodes**. Two control planes are consumed strictly
through their public interfaces and are never read from as source:

- **Remnawave Panel** (`docker-stack-iac`, `roles/infra/tasks/remnawave_tasks.yml`):
  the control plane that manages users/subscriptions and pushes config to nodes.
  The only inputs a node needs are `NODE_PORT` and `SECRET_KEY`, generated by the
  Panel when the node is created; the operator copies them into this project's
  vault. The Panel pushes the config — nodes are managed *by* the Panel, they do
  not configure the Panel.
- **NetBird management server** (`netbird-iac`): the self-hosted mesh control
  plane. A node joins as a peer with a **management URL + a setup key**, both held
  in this project's vault (never resolved from netbird-iac's vars/vault).

The central observability stack (`docker-stack-iac`, Prometheus/Grafana/Loki)
discovers peers from the NetBird API and scrapes `:9100` (node_exporter) and
`:6060` (CrowdSec LAPI) over the overlay. Enrolling with the `endpoint` setup key
(the default) makes a node discoverable with no exit/LAN routes.

## Inventory and node types

Managed nodes live in `inventory/hosts.yml` (local-only/gitignored; committed
template `inventory/hosts.yml.example`) and are never hardcoded into docs, roles,
or templates. Every managed host is in the single `remnawave_nodes` group, which
is the play target for every playbook; `group_vars/remnawave_nodes/main.yml`
enables monitoring by default. Per-host settings live in
`inventory/host_vars/<hostname>/main.yml`.

## The node lifecycle

1. `playbooks/bootstrap.yml` (`make host-bootstrap`) — optional, one host at a
   time. Probes `[ansible, admin, root]`, creates/repairs the least-privilege
   `ansible` service account, ensures Docker Engine + Compose v2, applies optional
   mirrors and authorizes configured SSH public keys. Never part of `site.yml`.
2. `roles/monitoring` (`make monitoring`, or as part of `site.yml`) — installs
   `prometheus-node-exporter`, `crowdsec` and `crowdsec-firewall-bouncer` and
   **includes `roles/agent`** to join the overlay (so the exporters are reachable
   without a public port).
3. `roles/remnanode` (part of `site.yml`) — renders and runs the Remnawave Node.

`make deploy` runs bootstrap, then `site.yml` (monitoring + remnanode). Use
`TAGS=monitoring` / `TAGS=remnanode` to run one part.

## Supported platform

Debian-family Linux with Docker Engine + Compose v2. When Docker is missing the
preflight installs Docker CE via Docker's official install script
(`https://get.docker.com`; disable with `install_docker: false`, which then fails
with install guidance). Non-Debian support is best-effort; automatic install is
Debian-only. CrowdSec and the nftables firewall bouncer are installed from the
Debian repositories (present in Debian 13 / trixie).

## Secrets and local-only files

- `inventory/host_vars/<hostname>/vault.yml` — **gitignored, never committed**
  (even encrypted). The single per-host encrypted vault holding everything:
  the operator-supplied topology (`vault_host.{ip,port}`), the SSH identities
  (`vault_root_*` / `vault_ansible_*` / `vault_host_admin_*`), the NetBird inputs
  (`vault_netbird_management_url`, `vault_netbird_setup_key`), the Remnawave node
  join credentials (`vault_remnanode_node_port`, `vault_remnanode_secret_key`),
  and the control-generated service-account password
  (`vault_host_ansible_password`, and `vault_host_admin_password` only when
  `host_admin_enabled` is set). Schema reference:
  `inventory/host_vars/example/vault.yml.example`.
- Vault password file: `~/.config/projects/remnawave-nodes-iac/ansible_vault_password`
  (pointed to by `ansible.cfg`; auto-generated by `make vault-init`). An
  encrypted vault cannot be read without it.
- `SECRET_KEY` is a live credential: the Panel authenticates the node with it.
  Treat `vault.yml` as sensitive; restrict `NODE_PORT` in the host firewall to the
  Panel's address only.

## Commands

- Control-node prerequisites: ansible-core within the supported range (pinned in
  `.tool-versions`, currently 2.19.x; asserted by the `playbooks/site.yml`
  preflight), Python 3, `openssl`, and the Galaxy collections from
  `requirements.yml`.
- `make install` — install the pinned toolchain (mise/asdf), the Galaxy
  collections, `sshpass`, and Keychain 3. Keychain is a fallback ssh-agent used
  only when a configured private key has permissions OpenSSH rejects (e.g. WSL
  `/mnt/c`); every SSH-consuming target runs through the shared
  `scripts/run-with-ssh-agent.sh`.
- `make vault-init` / `vault-view [HOST=]` / `vault-edit HOST=` — manage the vault
  password file and the per-host encrypted vault.
- `make host-init HOST=<name>` — scaffold `inventory/hosts.yml` (from the
  committed `example/` when absent) and `inventory/host_vars/<name>/`, encrypt the
  scaffolded `vault.yml`, and **ensure `<name>` exists under
  `remnawave_nodes.hosts` in `inventory/hosts.yml`** (idempotent; HOST defaults to
  `remnanode-1`). The scaffolded files are rendered **comment-free** from the
  committed `example/` templates (which stay as the documented reference) by
  `scripts/render_clean_template.py`; the inventory edit is line-based and
  comment-preserving (`scripts/ensure_inventory_host.py`) and an already-present
  host leaves the file untouched.
- `make host-bootstrap [HOST=]` — host init only (service account + Docker +
  mirrors). `make deploy` runs it first.
- `make agent` / `make monitoring` — the overlay join and the host
  monitoring/security parts.
- `make dry-run` / `make deploy` — preview / one-shot deploy.
- The internal `make lint` (`--syntax-check` + `ansible-lint`) is run by CI and
  hidden from `make help`.
- `make print [HOST=]` — resolved host vars incl. decrypted vault.

## Important gotchas

- A node's `NODE_PORT` must be reachable only from the Panel. This project does
  not manage a base firewall; restrict the port at the host/cloud firewall. The
  CrowdSec firewall bouncer only enforces CrowdSec decisions.
- The Remnawave Node image only publishes moving tags (`latest` / `sha-*`), so the
  default `remnanode_version: latest` cannot be pinned; Renovate tracks it for
  manual review. The Panel generates `remnawave/node:latest`.
- A rendered `docker-compose.yml` holds the live `SECRET_KEY`; it is mode `0600`
  and the render task is `no_log`. Never commit it (gitignored).
- Changing `NODE_PORT` / `SECRET_KEY` re-renders the compose file and recreates
  the container; keep the vault in sync with the Panel's node definition.
- The NetBird agent stores the management URL in `/var/lib/netbird/default.json`;
  the persisted value wins over `NB_MANAGEMENT_URL`. Changing the management URL
  needs a fresh setup key and a reset of the `netbird_config` volume (new peer),
  or an in-container `netbird up --management-url <new>`.
- node_exporter binds `127.0.0.1:9100` plus the overlay address
  (`roles/monitoring`); the central Prometheus reaches the overlay address.
- `roles/monitoring` gathers facts itself so non-opted hosts (`monitoring_enabled:
  false`) are never contacted by `playbooks/monitoring.yml`.
- The deploy **requires the non-root service account**: `playbooks/site.yml`
  asserts `host_ssh_user != root` (override with `host_allow_root_login=true`).
- The vault file must never stay plaintext: `write_vault` always encrypts, and a
  plaintext `vault.yml` is re-encrypted on the next write by the vault helpers.

## Role layout

- `playbooks/bootstrap.yml` — optional host tuning (service account, Docker,
  mirrors, SSH keys). Debian-family only for APT.
- `playbooks/agent.yml` / `playbooks/monitoring.yml` — focused entry points for
  the overlay join and host monitoring/security.
- `playbooks/site.yml` — preflight (ansible-core range, non-root) + the
  `monitoring` and `remnanode` roles.
- `playbooks/host_keys.yml` / `playbooks/ssh_agent_load.yml` — SSH host-key
  refresh and ssh-agent key loading (control node).
- `roles/helpers/` — a real role (no `tasks/main.yml`), always invoked via
  `include_role` + `tasks_from`: `control_node_prereqs.yml`,
  `install_docker.yml`, `read_vault.yml` / `write_vault.yml`,
  `dispatch_secrets.yml` / `generate_secrets.yml`.
- `roles/agent/` — joins a node to the overlay (the NetBird agent container, in
  `agent_dir` = `/opt/netbird-agent`). `peer_setup_key` +
  `netbird_management_url` come from this project's vault;
  `netbird_agent_routing: true` enables IP forwarding.
- `roles/monitoring/` — optional, opt-in (default on for nodes).
  Apt-installs `prometheus-node-exporter` + `crowdsec` +
  `crowdsec-firewall-bouncer` on a Debian-family host and includes the `agent`
  role; skipped unless `monitoring_enabled: true`.
- `roles/remnanode/` — renders and runs the Remnawave Node container (in
  `remnanode_dir` = `/opt/remnanode`).

## Scope

- **In scope**: the Remnawave proxy node container; the NetBird overlay agent; host
  monitoring/security (node_exporter, CrowdSec, nftables firewall bouncer); host
  bootstrap (service account, Docker, mirrors).
- **Out of scope (here)**: the Remnawave Panel and its database (docker-stack-iac);
  the NetBird management server and tenant config-as-code (netbird-iac); the
  central Prometheus/Grafana/Loki stack (docker-stack-iac); any base firewall
  management beyond CrowdSec.
